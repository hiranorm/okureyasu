# 評価

## iteration-1（2026-11-13、0.1.0 の草稿）

### やり方

- ケースは `evals/` の 7 場面: 技術の説明（tech-explain）、テスト失敗の報告（test-failure-report）、パスワードを預かる依頼の断り（refuse-credentials）、本番 DB を消す SQL の依頼（destructive-confirm）、疲れた人との雑談（casual-tired）、コードレビュー（code-review-ikezu）、AI っぽい文の言い換え（convert-text）。
- ほぼ同じプロンプトを、スキルを読ませたサブエージェントと、何も読ませないサブエージェント（Claude Opus 5.5）に答えさせた。destructive-confirm だけ、スキルなしは `/okureyasu` の代わりに「京ことばで頼むわ」を入れている。スキルなしにも「京都弁で」「京ことばで」と頼んでいるので、比べているのは「モデルが自力で書く京都弁」と「okureyasu を使った京ことば」。
- 採点は、`okureyasu_lint.py` の error 件数（機械）と、各ケース 4〜5 項目の確認（スキルの作者が自分で読んで付けた）。
- 結果の生データは `okureyasu-workspace/iteration-1/`（git 管理外）。

### この結果の限界

- 各ケース 1 回ずつ（n=1）で、ばらつきは見ていない。
- 採点はスキルの作者による自己採点。
- 7 件中 3 件（casual-tired、refuse-credentials、test-failure-report）は examples.md の例とほぼ同じ場面で、実行役は examples.md を読んでいた。refuse-credentials の返答は例 3 とほぼ同じ文だった。
- スキルありの実行役は、自分で lint を回して直してから保存していた。会話での実使用（初稿がそのまま出る）とは条件が違う。
- 「〜まへん」「〜まひょ」は京都でも聞かれる形で、warn はスキルの方針（使わない）との違いを数えたもの。京都らしくない形として数えたのは error だけ。

これを受けて、例と重ならない場面を lint なしで走らせ直したのが iteration-2。

### 結果

| | スキルあり | スキルなし |
|---|---|---|
| 確認項目の通過率 | 100%（29/29） | 66%（19/29） |
| lint の error（京都らしくない形） | 0 件 | 7 件（7 ケース中 6 ケース） |
| lint の warn（スキルの方針と違う形） | 0 件 | 18 件（ほぼ「〜まへん」） |
| 太字 | 0 か所 | 27 か所 |
| 見出し | 0 個 | 27 個 |
| 返答の長さ（7 件合計） | 4,689 字 | 7,244 字 |

スキルなしで出た京都らしくない形:

- せや、せやし、せやさかい、せやけど（5 ケース）
- おます（2 ケース。大阪の「おす」）
- 選びはった（5 段動詞の連用形に「はる」。京都は「選ばはった」）

ほかに目に付いた違い:

- スキルなしの技術の説明は「ええとこ突いてきはりますなあ」で始まった（AI の冒頭の称賛を京都弁にしただけ）。コードブロックの中のコメントにも京都弁が入った。
- スキルなしの言い換えは「！🎉」を残し、「いかがでしたか」を「どないどした？」に訳した。AI の定型を消さずに京都弁を振りかけた形。
- スキルなしのコードレビューのいけずは、書いた本人に向いていた（「書かはったご本人さんしか読めへんよう、よう工夫してはりますこと」）。スキルありは、コードに向けて1つだけ言い、すぐ「ほんまのこと言うたら」と本音に移った。
- スキルなしは「float で 1 円ずれることがあります」と言い切ったが、スキルありは「今の範囲では同じ値になる」と確かめたうえで整数演算を勧めた（言い切りの強さを事実に合わせている）。
- 断りと危険な操作の確認は、どちらもはっきりできていた。この 2 ケースはモデルの既定の振る舞いが強く、スキルの有無で差が出にくい。

### 見つかった問題と手当て

- casual-tired のスキルありの返答が、examples.md の例文をほぼそのまま写していた。評価の場面が例と同じだったため。examples.md の雑談の例を別の場面に替え、「例は型を借りるもので、言い回しは写さない」と書き足した。
- convert-text のスキルありの返答は、外した装飾をインラインコードで書いて lint を避けていた。言い換えモードでは「返すのは言い換えた文章。外した装飾は本文の後に一行だけ」と SKILL.md に明記した。
- lint の誤検出: 「どないどした？」の「ないどした」を形容詞＋どすと拾った。除外を足し、回帰テストに入れた。
- lint の検出漏れ: 「〜まひょ」を拾えなかった。ルールを足した。

## iteration-2（2026-11-13、iteration-1 の後の修正を入れた版）

### やり方

- examples.md の例と重ならない 6 場面: あっさりの指定（level-assari、git の rebase と merge）、こってりの指定（level-kotteri、資料が間に合わないときの上司への伝え方）、`/okureyasu` だけで直前の返答を言い直す（bare-resay）、docstring とコミットメッセージを書かせる（artifacts-standard）、他人の会員のメールアドレスを集めるスクリプトの依頼（refuse-scraping）、TypeScript のビルドエラー（build-failure）。
- スキルありだけを走らせた。実行役には Read と Write しか使わせず、lint も回させていない（初稿をそのまま見る）。lint は後から作者がかけた。

### 結果

| | スキルあり |
|---|---|
| 確認項目の通過率 | 100%（24/24） |
| lint の error / warn | 0 / 0（6 件とも初稿のまま） |

- あっさりは「どす」「おす」を使わず、「〜へん」「そやし」で京都の話し言葉にしていた。
- こってりは「よろしゅうございます」「〜とおくれやす」「おきばりやす」で話し、上司に送る文面の例だけは標準語のまま残した（ファイルや外に出るものは標準語、という規則どおり）。
- `/okureyasu` だけのときは、前の返答の 4 項目、コード片、「よくある」の確度を落とさずに言い直した。
- docstring とコミットメッセージは標準語のまま、地の文だけが京ことばだった。
- 断りは 1 文目で言い切り、理由（個人情報、不正アクセス）と正当な代わりの道を示した。いけずは使っていない。

### この結果の限界

- iteration-1 と同じく n=1、自己採点。
- 6 件ともスキルなしとの比較はしていない（スキルなしの京都弁の誤りは iteration-1 で見た）。

### 次に試すこと

- 長い会話での振る舞い（途中で濃さを変える、いけずや「ほな」が回を追って増えないか、話し手がぶれないか）。
- 同じケースを複数回走らせてばらつきを見る。
- 京都出身の話者に、スキルありの返答を読んでもらう。
